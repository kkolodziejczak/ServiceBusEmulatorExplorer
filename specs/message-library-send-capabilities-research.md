# Message-library sender capabilities research

Researched 2026-09-19 against the current [message-library implementation plan](message-library-implementation-plan.md), the pinned `Azure.Messaging.ServiceBus` 7.20.1 package, and Microsoft’s current Azure Service Bus documentation. This note records evidence and recommendations; it does not approve a broader product-contract change.

## Scope and version boundary

The repository pins [`Azure.Messaging.ServiceBus` 7.20.1](../src/ServiceBusEmulatorExplorer.Core/ServiceBusEmulatorExplorer.Core.csproj). The version-tagged sender source confirms that 7.20.1 exposes `ScheduleMessagesAsync(IEnumerable<ServiceBusMessage>, DateTimeOffset, CancellationToken)` and returns scheduled-message sequence numbers ([7.20.1 sender source](https://raw.githubusercontent.com/Azure/azure-sdk-for-net/Azure.Messaging.ServiceBus_7.20.1/sdk/servicebus/Azure.Messaging.ServiceBus/src/Sender/ServiceBusSender.cs)). The current API pages resolve to 7.20.2 ([current scheduling API](https://learn.microsoft.com/en-us/dotnet/api/azure.messaging.servicebus.servicebussender.schedulemessagesasync?view=azure-dotnet), [current send API](https://learn.microsoft.com/en-us/dotnet/api/azure.messaging.servicebus.servicebussender.sendmessagesasync?view=azure-dotnet)); current-page behavior must be rechecked if the package is upgraded.

The pinned [7.20.1 `ServiceBusMessage` source](https://raw.githubusercontent.com/Azure/azure-sdk-for-net/Azure.Messaging.ServiceBus_7.20.1/sdk/servicebus/Azure.Messaging.ServiceBus/src/Primitives/ServiceBusMessage.cs) is the source of truth for the property coverage below. Its public message model exposes binary `Body`, broker properties, `ApplicationProperties`, `ScheduledEnqueueTime`, and `GetRawAmqpMessage()`; the current docs are useful for behavior but are not a substitute for the pinned source.

## Findings for the approved send direction

The existing plan’s v1 schema intentionally omits destination, profile, original `MessageId`, scheduled time, TTL, credentials and broker observation metadata; a new send gets a separate transport `MessageId` ([plan, schema rules](message-library-implementation-plan.md)). The plan also specifies one SDK call per CSV row, sequential order, no transactions, no duplicate-detection guarantee and no exactly-once claim ([plan, send lifecycle](message-library-implementation-plan.md)).

The approved scheduling choice is one UTC schedule instant for the whole reviewed batch. There is no per-row schedule column or CSV schedule expression. The coordinator’s plan amendment calls for scheduling prepared rows sequentially with `ScheduleMessageAsync` at that same instant and retaining each returned sequence number as a cancellation receipt. The SDK also exposes `ScheduleMessagesAsync` for an atomic set operation: all messages are scheduled or none are, with no partial success ([7.20.1 sender source](https://raw.githubusercontent.com/Azure/azure-sdk-for-net/Azure.Messaging.ServiceBus_7.20.1/sdk/servicebus/Azure.Messaging.ServiceBus/src/Sender/ServiceBusSender.cs), [single-message API](https://learn.microsoft.com/en-us/dotnet/api/azure.messaging.servicebus.servicebussender.schedulemessageasync?view=azure-dotnet)). Either API is atomic at its own request boundary, not simultaneous delivery: Service Bus says the actual enqueue/activation time depends on workload and state, and the requested time may not be exact ([scheduled messages](https://learn.microsoft.com/en-us/azure/service-bus-messaging/message-sequencing#scheduled-messages), [pinned `ScheduledEnqueueTime` remarks](https://raw.githubusercontent.com/Azure/azure-sdk-for-net/Azure.Messaging.ServiceBus_7.20.1/sdk/servicebus/Azure.Messaging.ServiceBus/src/Primitives/ServiceBusMessage.cs)).

Cancellation requires the broker-issued sequence numbers and `CancelScheduledMessagesAsync(IEnumerable<long>, CancellationToken)` ([cancellation API](https://learn.microsoft.com/en-us/dotnet/api/azure.messaging.servicebus.servicebussender.cancelscheduledmessagesasync?view=azure-dotnet)). Sequence numbers are valid only while messages remain scheduled; activation assigns a new active-message sequence number. Cancellation deletes scheduled messages. Activation and cancellation are independent operations without mutual locking, so a near-deadline cancel can race activation and leave a message active; the UI must expose a cancellation result rather than claim rollback ([scheduled-message lifecycle and race](https://learn.microsoft.com/en-us/azure/service-bus-messaging/message-sequencing#scheduled-messages)). A receipt store should therefore retain run ID, destination identity, row index, `MessageId`, schedule time, sequence number and terminal cancellation state for the session; it must treat an uncertain cancel response as uncertain.

The coordinator’s scheduling amendment also calls for these local outcome rules: stopping does not silently cancel schedules that were already accepted; cancellation is an explicit follow-up action. If the common target time elapses before the next SDK call, the approved plan stops submission and marks that row and the remaining rows Not attempted; it never silently switches to immediate send. A request already in flight remains subject to acknowledgement/unknown-outcome accounting. A call that started but has no trustworthy response remains outcome-unknown. The scheduled path should use a conservative encoded-size ceiling during preflight, and tests should cover sequential receipt assignment, stop before/during/after submission, elapsed target time, partial schedule failure, uncertain cancellation and duplicate-click prevention. These are implementation recommendations from the current plan amendment, not additional Azure guarantees.

TTL is a relative duration. For scheduled messages, expiration is based on the enqueue/activation time, not the earlier client send time: a message scheduled five minutes out with a ten-minute TTL expires about fifteen minutes from the original send, subject to entity limits ([message expiration and scheduled messages](https://learn.microsoft.com/en-us/azure/service-bus-messaging/message-expiration)). The entity default TTL is a ceiling and a longer message TTL may be silently adjusted. The current plan has no TTL field, so exposing TTL requires a schema and review-contract decision; if later added, show the requested duration and the entity-ceiling limitation rather than implying an exact wall-clock expiration.

Duplicate detection is a broker entity feature supported by Standard and Premium, not Basic. It uses the application-controlled `MessageId`; the documented default history window is 10 minutes, with a 20-second minimum and seven-day maximum. Scheduled messages participate in the same duplicate-detection rule: a duplicate scheduled/non-scheduled submission can be acknowledged as accepted by the send operation and then dropped, so an SDK success is not proof that a retained message exists ([duplicate detection](https://learn.microsoft.com/en-us/azure/service-bus-messaging/duplicate-detection)). The documentation establishes inclusion but does not define a product guarantee for a far-future schedule relative to the history window. Do not promise deduplication for that case; the safe v1 behavior remains generated fixed IDs plus no exactly-once claim. A future retry design would need to make the duplicate window, schedule horizon and outcome-unknown handling explicit.

## Batching and transactions

The SDK supports safe size-bounded batching through `CreateMessageBatchAsync`/`TryAddMessage` and `SendMessagesAsync(ServiceBusMessageBatch)`. The `IEnumerable<ServiceBusMessage>` overload attempts one service batch and fails if the messages exceed the maximum batch size; the batch send API documents an all-or-none result for that batch ([send API](https://learn.microsoft.com/en-us/dotnet/api/azure.messaging.servicebus.servicebussender.sendmessagesasync?view=azure-dotnet), [client-library batching example](https://learn.microsoft.com/en-us/dotnet/api/overview/azure/messaging.servicebus-readme?view=azure-dotnet)). This provides an atomic send operation for the batch, but it is not a general transaction across multiple operations and it weakens the current plan’s per-row outcome boundary. Keep the existing one-message preflight and sequential send for v1 unless a later contract explicitly changes result accounting.

Service Bus transactions can group send/settlement operations against messaging entities and commit them as one unit. Basic does not support transactions; Standard and Premium do. Management operations cannot be mixed with messaging operations, and the service does not retry an operation that fails inside a transaction ([transactions](https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-transactions)). The current plan defers transactions and has no transaction-partition-key field. Treat transaction support as a later scope requiring a destination-tier check, an explicit transaction outcome model and independent broker proof.

## Emulator evidence boundary

Microsoft’s emulator documentation lists known limitations (no partitioned entities, no AMQP WebSockets, no persistence across container restart) and quotas including a listed one-hour configurable message TTL quota and 256 KB message size ([emulator overview](https://learn.microsoft.com/en-us/azure/service-bus-messaging/overview-emulator)). The current page explicitly supports entity management through the Service Bus Administration Client; older claims that SDK administration is unavailable are stale. It is not a complete compatibility matrix for scheduling, cancellation, duplicate detection and transactions, so absence from this overview does not establish lack of support. No emulator run was performed for this read-only research pass. Therefore those behaviors must be labeled unverified for the local emulator and proved against a supported cloud namespace or a dedicated emulator test when implementation is authorized; do not infer support from the cloud API surface.

## Sender property coverage against the pinned SDK

The current plan’s capture/schema fields cover only a subset of the sender’s public message model. The payload documentation distinguishes an opaque binary payload, predefined broker properties and user application properties ([message payload model](https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-messages-payloads)). The table maps the 14 user-relevant `ServiceBusMessage` properties to current plan behavior. “Recommend” is a future capability suggestion, not approval.

| SDK property | Current plan / capture status | Recommendation or boundary |
|---|---|---|
| `Body` | JSON/text body, including empty text and metadata-only messages, is covered; binary capture is deferred and must be explicit | Preserve exact UTF-8 prepared bytes; keep binary out of v1 until a binary template contract exists |
| `MessageId` | Generated per new send; custom/captured value is missing | Keep generated fixed IDs for v1; custom IDs require a duplicate-detection and retry decision |
| `PartitionKey` | Missing | Advanced capability; emulator does not support partitioned entities, so defer |
| `TransactionPartitionKey` | Missing | Defer with transactions; it selects transfer-queue partitioning ([pinned source](https://raw.githubusercontent.com/Azure/azure-sdk-for-net/Azure.Messaging.ServiceBus_7.20.1/sdk/servicebus/Azure.Messaging.ServiceBus/src/Primitives/ServiceBusMessage.cs)) |
| `SessionId` | Covered in reusable properties | Validate against the selected destination’s session requirement |
| `ReplyToSessionId` | Missing | Recommend a later typed property; it augments `ReplyTo` with the reply session ([pinned source](https://raw.githubusercontent.com/Azure/azure-sdk-for-net/Azure.Messaging.ServiceBus_7.20.1/sdk/servicebus/Azure.Messaging.ServiceBus/src/Primitives/ServiceBusMessage.cs)) |
| `TimeToLive` | Missing | Recommend a later field with entity-ceiling and scheduled-enqueue semantics |
| `CorrelationId` | Covered | Preserve exact value and avoid legacy trimming |
| `Subject` | Covered | Preserve exact value; it is the standardized application subject |
| `To` | Missing | Low priority logical metadata only; the broker currently ignores it for routing, so it must never replace the selected destination ([pinned source](https://raw.githubusercontent.com/Azure/azure-sdk-for-net/Azure.Messaging.ServiceBus_7.20.1/sdk/servicebus/Azure.Messaging.ServiceBus/src/Primitives/ServiceBusMessage.cs)) |
| `ContentType` | Covered | Preserve exact descriptor |
| `ReplyTo` | Missing | Recommend a later typed reply path; it is application-defined metadata, not the send destination |
| `ScheduledEnqueueTime` | Newly approved as one common batch instant | Use one UTC `DateTimeOffset` for the whole reviewed batch and retain sequence receipts; no per-row CSV scheduling |
| `ApplicationProperties` | Subset only: `string`, `bool`, `int64`, `double`; other SDK-supported types are omitted/lost by capture | Keep the explicit v1 subset; broader typed capture is a future schema decision. The SDK property accepts `IDictionary<string, object>` but serialization rejects unsupported values and has a documented `byte[]` limitation ([API](https://learn.microsoft.com/en-us/dotnet/api/azure.messaging.servicebus.servicebusmessage.applicationproperties?view=azure-dotnet), [pinned source](https://raw.githubusercontent.com/Azure/azure-sdk-for-net/Azure.Messaging.ServiceBus_7.20.1/sdk/servicebus/Azure.Messaging.ServiceBus/src/Primitives/ServiceBusMessage.cs)) |

`GetRawAmqpMessage()` is an additional advanced escape hatch rather than one of the 14 ordinary properties. It can expose AMQP headers, footers, annotations and other data outside the typed surface; defer it because persisting arbitrary AMQP data would expand the schema and exact-preview/security contract. Broader binary payloads, raw AMQP metadata and transactions remain deliberate deferrals ([pinned 7.20.1 source](https://raw.githubusercontent.com/Azure/azure-sdk-for-net/Azure.Messaging.ServiceBus_7.20.1/sdk/servicebus/Azure.Messaging.ServiceBus/src/Primitives/ServiceBusMessage.cs)).

## Capability matrix

Coordinator recommendation for the next scope decision: add TTL, optional custom MessageId (generated remains default), ReplyTo/ReplyToSessionId, explicit scheduled-message cancellation, and broader typed application-property capture. These are useful for an operational message authoring tool, but only common-time scheduling has been approved so far. Keep PartitionKey as an optional cloud-oriented advanced field; retain transactions, TransactionPartitionKey, raw AMQP editing and binary templates as deliberate deferrals. The narrower recommendations in the table below describe the current approved boundary, not a decision that these gaps should never be filled.

For broader metadata capture, the pinned SDK documents more types than the plan currently represents, including Guid, decimal, DateTime/DateTimeOffset, TimeSpan, Uri and multiple integer widths. A future schema must preserve declared type and precision rather than stringify silently. Binary application properties have a documented service limitation; they are distinct from binary message bodies. The Azure quota reference also imposes per-property and cumulative-header limits, so whole-message size checks alone should not be presented as complete property validation ([application-property types](https://learn.microsoft.com/en-us/dotnet/api/azure.messaging.servicebus.servicebusmessage.applicationproperties?view=azure-dotnet), [message property limits](https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-quotas)).

Capture is not a constructor-level clone: the pinned SDK's received-message copy constructor deliberately excludes broker-generated delivery annotations, DLQ reason/description and the prior diagnostic trace ID. Review the application's allowlist against those exclusions when implementing capture so a fresh message does not inherit misleading provenance ([pinned copy constructor](https://raw.githubusercontent.com/Azure/azure-sdk-for-net/Azure.Messaging.ServiceBus_7.20.1/sdk/servicebus/Azure.Messaging.ServiceBus/src/Primitives/ServiceBusMessage.cs)).

| Capability | Existing plan | Missing or unverified | Recommendation |
|---|---|---|---|
| One common schedule time for a reviewed batch | Not in v1 schema; now approved product direction | Emulator support and real-cloud timing proof are unverified here | Add as a dedicated scheduled-run path with one UTC instant and per-row sequence receipts |
| Cancel scheduled run | Not specified | Cancellation/activation race must be handled; emulator support is undocumented | Add explicit cancel action and uncertain outcome state; report a cancellation acknowledgement separately from any guarantee that activation was prevented |
| TTL | Explicitly a v1 non-goal | Scheduled TTL starts at activation; emulator max is one hour | Defer until schema, review, entity ceiling and display semantics are approved |
| Duplicate detection | No guarantee; generated IDs and no retry | Cloud feature depends on entity tier/window; far-future schedule interaction is not promised | Keep no exactly-once claim and document duplicate-detection limits |
| Native message batching | Used for one-message encoded-size preflight; sends are sequential per row | Batch all-or-none result conflicts with per-row outcome accounting | Defer send batching unless the result contract changes |
| Transactions | Explicitly deferred | Tier and emulator compatibility unverified; management calls cannot join | Defer to a separately approved transaction contract |
| Full sender-property capture | Explicit subset and omission rules | Binary, routing/partition, reply, TTL and raw AMQP data are incomplete | Preserve the narrow v1 subset and make omissions visible during capture |
