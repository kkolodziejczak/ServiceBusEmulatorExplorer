WPF Service Bus Emulator Explorer MVP

Implementation-ready MVP plan for a Windows desktop application that connects directly to a local Azure Service Bus emulator, shows queues, topics, subscriptions, active messages, and dead letter messages, and provides explicit non-destructive DLQ replay controls.

Goal

Ship a small, reliable WPF explorer for local development against the Azure Service Bus emulator. The app should make common emulator inspection and recovery tasks fast without requiring the example Minimal API, a browser UI, Azure portal access, or manual AMQP tooling.

North-star constraint: DLQ operations must be explicit and non-destructive by default. Replaying a DLQ message creates a new message and leaves the original DLQ message untouched unless the user chooses a separate delete action.

Summary

The MVP is a single Windows desktop app built with WPF on net10.0-windows, using Azure.Messaging.ServiceBus and Azure.Messaging.ServiceBus.Administration directly. The app stores local connection profiles, connects to the emulator, presents a navigation tree for queues and topics, shows entity details and message grids, and offers safe commands for send, peek, replay, and delete.

"CRUD" in this spec means full management for Service Bus entities where the SDK supports it. Message operations are not true CRUD: messages are created by send, inspected by peek/receive, removed by receive completion, and replayed by cloning into a new message.

Scope And Non-goals

In Scope

  • Connect to local Service Bus emulator using direct Azure SDK clients.
  • Save and reuse local connection profiles in user-scoped app settings.
  • List queues, topics, and topic subscriptions with active, scheduled, and DLQ counts where available.
  • Create, edit metadata where SDK-supported, and delete queues, topics, and subscriptions.
  • Send messages to queues and topics with body, content type, correlation id, session id, subject, and application properties.
  • Peek active and DLQ messages without locking or removing them.
  • Inspect full message body, system properties, and application properties.
  • Display all Service Bus dates and log timestamps in UTC with explicit labels or a trailing Z.
  • Replay DLQ messages by creating a new message with a new MessageId, optionally editing body and application properties.
  • Delete selected DLQ messages only through explicit delete commands.
  • Bulk delete selected DLQ messages and, behind a stronger confirmation, all visible DLQ messages.

Non-goals For MVP

  • No Azure cloud namespace support beyond connection strings that the SDK accepts.
  • No rule/filter CRUD for subscriptions in Stage 1.
  • No scheduled message authoring in Stage 1.
  • No sessions workflow beyond displaying and preserving SessionId on replay when requested.
  • No long-running background polling by default. Manual refresh is primary; optional short interval refresh is allowed.
  • No custom Minimal API host or browser UI in this repository.

  Receiver->>Emulator: Lock matching DLQ message
  Emulator-->>Receiver: Locked DLQ message
  Replay->>Replay: Clone body and selected properties
  Replay->>Replay: Assign new MessageId
  Replay->>Sender: Send cloned message to queue or topic
  Sender->>Emulator: Enqueue active message

  Replay->>Receiver: Abandon original DLQ lock
  Receiver->>Emulator: Return DLQ message unchanged
  Replay-->>UI: Report new MessageId and original status

Amendment: Modern ServiceBusExplorer-Inspired UI

The WPF MVP should follow the interaction model of the common open-source ServiceBusExplorer desktop application, while using a modern WPF visual treatment and keeping this project's own emulator-first branding, implementation, and DLQ safety rules.

BeforeAfterReason
Legacy/old-school ServiceBusExplorer visual treatment with WinForms-like blue gradients and beveled panes. Modern desktop shell with clean command bar, neutral panes, left namespace tree, tabbed entity view, message list, message text/properties panels, bottom action row, and log pane. User wants the familiar ServiceBusExplorer workflow, but the app can and should look modern.
DLQ controls shown as generic toolbar commands near the grid. DLQ controls follow the Messages/Dead Letter tab workflow, with Replay DLQ Copy, Edit and Replay DLQ, Delete Selected DLQ, and Delete Visible DLQ commands in the bottom action strip. Matches the expected Windows explorer workflow while preserving non-destructive replay as the default.
Wireframe included reference-tool conveniences not yet in the MVP contract, such as import/export, authorization-rule tabs, metrics tabs, receive, ambiguous messages command, and a global DLQ workbench. Wireframe only shows commands and tabs covered by the MVP scope: connection, entity create/update/delete, message send/peek/copy, per-entity active/DLQ inspection, replay, explicit delete, refresh, and operation logging. User wants implementation to match what is visible in the wireframe without hidden extra scope.

Amendment: Test-First MVP

Testing is part of the first implementation slice. The MVP should not wait for stable behavior before creating tests; it should use early tests to create that stability.

BeforeAfterReason
Automated WPF UI tests were optional and could follow after MVP stability. A small gated FlaUI/UIA3 smoke suite starts in Stage 1 as soon as the first WPF shell exists. Early UI smoke tests catch regressions in app launch, shell wiring, and command visibility before feature work stacks up.
Integration test hardening was concentrated near packaging. Integration test project and readiness fixture are created in Stage 1, with feature-specific integration tests added as the related behavior is implemented. Docker-backed tests should evolve with the Service Bus service layer, not arrive as a late verification phase.

Amendment: Compact Action Buttons

The bottom action strip should use compact icon-plus-label buttons instead of long text-only labels. The short visible labels reduce horizontal overflow, while full command names remain available through tooltips, automation names, and view model command names.

BeforeAfterReason
Long text-only buttons such as Send New Message, Edit and Replay DLQ, and Delete Selected DLQ. Compact icon-plus-label buttons such as Send, Replay, Edit Replay, Selected, and Visible, with full accessible names. Fits the desktop action strip better and keeps frequent commands scan-friendly without losing command meaning.

Code Organization Constraints

  • Prefer CUPID-friendly classes: composable, Unix-philosophy focused, predictable, idiomatic, and domain-based.
  • Order methods in files by invocation flow: public command method first, then private helpers directly below in the same order they are called.
  • Keep SDK-specific code inside service implementations. View models depend on interfaces and plain models.
  • Do not swallow SDK exceptions silently. Convert them into user-facing operation results with enough detail for local debugging.

DLQ Behavior

Command distinction: Send New Message starts from a blank user-authored message. Replay DLQ Copy clones the selected DLQ message into a new active message without editing. Edit and Replay DLQ opens the selected DLQ message as an editable draft and sends that draft as a new active message. Both replay commands leave the original DLQ message untouched.

CommandBehaviorOriginal DLQ messageConfirmation
Replay selected Receive selected DLQ message in PeekLock, clone body/properties, assign new MessageId, send to queue/topic, abandon original lock. Remains in DLQ. No destructive confirmation required.
Replay edited copy Open editor, let user change body/content/application properties, send edited clone with new MessageId. Remains in DLQ. No destructive confirmation required.
Delete selected Receive selected DLQ messages in PeekLock and complete them without replay. Removed. Requires confirmation.
Delete all visible Delete the currently loaded page of DLQ messages. Removed. Requires stronger typed confirmation.
Important implementation note: exact targeted deletion/replay should use SequenceNumber rather than MessageId. Duplicate message IDs are possible, and message ID alone is not a reliable unique handle in a queue or subscription.

Stage Plan

Stage 1: Working Shell And Connection

  • Create solution, WPF app, core library, and tests.
  • Create unit, integration, and UI smoke test projects immediately, even if most tests start with skipped or fixture-only coverage.
  • Add DI composition root and MVVM toolkit.
  • Implement connection profile model and local settings store.
  • Connect to emulator and show connection status.
  • Add smoke test for profile validation and client factory behavior using fakes.
  • Add FlaUI launch smoke test that starts the WPF shell, finds the main window, verifies the app title and connection controls, then closes the app.

Stage 2: Entity Browser

  • List queues, topics, and subscriptions through administration client.
  • Show counts and metadata in navigation and detail header.
  • Implement manual refresh with cancellation and visible error states.
  • Add unit tests for tree shaping and metadata mapping.
  • Extend UI smoke tests to verify the namespace tree loads seeded entities and selecting a node updates the detail header.

Stage 3: Entity Management

  • Create queue, topic, and subscription dialogs.
  • Update supported metadata for queues, topics, and subscriptions.
  • Delete queue, topic, and subscription with confirmation.
  • Add tests for command validation and SDK request mapping.
  • Add UI smoke coverage for create/update/delete dialog opening, validation, and confirmation behavior.

Stage 4: Message Inspection And Send

  • Peek active and DLQ messages by page using sequence numbers.
  • Show message detail body and properties.
  • Send messages to queues and topics.
  • Add tests for message projection and send command mapping.
  • Add integration tests for send/peek and UI smoke coverage for selecting a message row and seeing body/properties update.

Stage 5: Full DLQ Control

  • Replay selected DLQ message with a new ID and leave original in DLQ.
  • Replay edited copy with optional body and application property changes.
  • Delete selected DLQ messages as an explicit destructive command.
  • Add tests proving replay does not delete the original by default.
  • Add UI smoke coverage for DLQ row selection, replay command enablement, and delete confirmation.

Stage 6: Test Hardening, Packaging, And Manual Proof

  • Keep root compose.yaml and .env.example as the supported local emulator test environment.
  • Add an integration test fixture that waits for the emulator administration endpoint to become usable before running tests.
  • Gate integration tests behind an explicit environment variable so ordinary unit test runs do not require Docker.
  • Add README quickstart for emulator connection and test data.
  • Add manual verification script using the local emulator compose setup.
  • Harden the FlaUI/UIA3 smoke suite so it is reliable locally and can be run explicitly without blocking fast unit-test loops.
  • Publish self-contained Windows build artifact.

Acceptance Criteria

  • App starts on Windows and shows a connection profile form without requiring any web service.
  • User can connect to a local Service Bus emulator using runtime and administration connection strings.
  • User can browse queues, topics, and subscriptions from the emulator.
  • User can create and delete queues, topics, and subscriptions.
  • User can edit supported entity metadata where the Azure SDK supports updates.
  • User can send a message to a queue or topic.
  • User can peek active messages without removing them.
  • User can peek DLQ messages without removing them.
  • User can inspect full message body, application properties, and system properties.
  • User can see all displayed entity dates, message dates, and log timestamps in UTC, with no ambiguous local-time-only labels.
  • User can replay a DLQ message with a new MessageId while the original remains in DLQ.
  • User can edit body/properties before replaying a DLQ copy.
  • User can delete selected DLQ messages only after explicit confirmation.
  • Integration tests can run against the repository Docker Compose emulator and verify queue/topic/subscription CRUD, send/peek, DLQ replay, and DLQ deletion.
  • UI smoke tests can launch the WPF app and verify the main shell controls as soon as the first shell exists.
  • Failed SDK operations show actionable errors and do not leave the UI in a false success state.

Risks, Assumptions, And Deferred Choices

Assumptions

  • The MVP targets Windows developer machines and local emulator workflows.
  • The emulator accepts the same SDK patterns used by the reference project.
  • net10.0-windows is acceptable because the reference project already uses .NET 10.
  • Subscription rules and filters are useful later, but not required for the first working MVP.

Risks

  • Targeted DLQ operations require careful sequence-number handling. Message ID is not enough.
  • Ambiguous local timestamps can cause incorrect troubleshooting. The MVP must label displayed timestamps as UTC and use DateTimeOffset internally.
  • Receive-and-delete mode is dangerous for DLQ. Prefer PeekLock plus explicit complete/abandon logic.
  • Some metadata updates may not be supported after entity creation or may behave differently in the emulator.
  • Docker startup can be slower than test startup. Integration tests must have bounded readiness polling instead of fixed sleeps.
  • WPF UI automation is slower and more environment-sensitive than service integration tests. Keep the automated UI suite small, gated, and focused on smoke workflows from the first shell onward.
  • Large message bodies can make the WPF grid sluggish if bound directly. Use previews in the grid and load full detail on selection.

Deferred Choices

  • Whether to add subscription rule/filter CRUD after MVP.
  • Whether to add import/export of messages as JSON files.
  • Whether to support Azure cloud namespaces with safer profile labeling.
  • Whether the gated FlaUI/UIA3 smoke tests should later run in CI or remain local-only for the MVP.

Definition Of Done

  • All Stage 1 through Stage 5 acceptance criteria pass locally.
  • Unit tests cover service contracts, view model command states, and DLQ replay default behavior.
  • Docker-backed integration tests pass when the root compose emulator is running and integration tests are explicitly enabled.
  • An intentionally small FlaUI/UIA3 smoke suite covers launch, connect, navigation, and DLQ command enablement behind SBE_RUN_UI_TESTS=true.
  • Manual proof confirms default replay leaves DLQ originals untouched.
  • Destructive operations require confirmation and report success/failure accurately.
  • README documents emulator startup, connection strings, and the DLQ workflow.
  • Code follows method ordering preference and keeps private helpers below their callers in invocation order.
