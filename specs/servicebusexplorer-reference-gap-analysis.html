Goal

Identify the highest-value Service Bus Explorer parity opportunities that fit this repository's local-emulator mission, and define testable implementation stages for those opportunities without diluting the existing MVP.

North-star constraint: keep the app focused on reliable local Azure Service Bus emulator operations unless the user explicitly expands scope to cloud namespaces or adjacent Azure messaging products.

Summary

The current application already implements the MVP slice well: WPF shell, connection profiles, queue/topic/subscription entity management, message send/peek, DLQ replay, explicit DLQ delete, integration tests, UI smoke tests, and a manual proof workflow. The reference repository suggests several next improvements, but only some are appropriate for this emulator-first tool.

P1 Wire and test Copy Body for active and DLQ messages. Reference tests explicitly cover this and local XAML already exposes a disabled button that says it is not wired. Unit command state tests, clipboard abstraction tests, and a small UI smoke check.

Existing State Findings

Current Application Capabilities

  • Connects to local Azure Service Bus emulator using separate runtime and administration connection strings.
  • Persists connection profiles and validates profile fields.
  • Browses queues, topics, and subscriptions in a namespace tree.
  • Creates, updates, and deletes queues, topics, and subscriptions.
  • Shows selected entity metadata and active, DLQ, scheduled, and total counts.
  • Filters loaded namespace entities through NamespaceFilter.
  • Sends messages to queues and topics.
  • Peeks active and DLQ messages for supported entity scopes with paging.
  • Shows selected message body, system properties, and application properties.
  • Replays selected DLQ messages as new active messages without deleting the original.
  • Deletes selected or visible DLQ messages only through explicit confirmation.

Current Test Coverage

  • Core unit tests cover connection validation, profile storage, message preview, replay ID policy, entity tree shaping, request mappers, validators, message projection, and DLQ replay mapping.
  • App unit tests cover shell profile load/connect/refresh, namespace filtering, entity workflow command states, topic subscription refresh failure isolation, send/peek behavior, DLQ command states, replay, edit replay, and delete confirmations.
  • Integration tests cover emulator readiness, entity CRUD, send/peek active and DLQ messages, topic subscription messages, non-destructive DLQ replay, and explicit DLQ delete.
  • UI smoke tests cover launch, connection/navigation, context-aware command visibility, entity dialogs, message detail rendering, DLQ command enablement, DLQ delete confirmation, and replay proof.

Notable Current Gaps

  • The XAML contains a visible Copy Body button, but it is intentionally disabled and not wired to a command.
  • No dashboard tab or all-entity count grid exists; counts are entity-detail scoped.
  • No auto-refresh interval or count-alert highlighting exists.
  • No grid row copy, name copy, TSV export, or context menu copy flow exists.
  • No active message receive/complete workflow exists; current message inspection is non-destructive except explicit DLQ delete.
  • No namespace import/export, Entra ID, Event Hubs, Relay, or Notification Hubs scope exists.

Scope And Non-goals

In Scope

  • Service Bus queue/topic/subscription workflows that can run against the local emulator.
  • Operator convenience improvements that reduce repetitive troubleshooting work.
  • Tests that convert manual/reference acceptance checks into automated local verification where feasible.
  • Preserving non-destructive defaults and explicit destructive confirmation.

Non-goals

  • No Entra ID sign-in unless the product scope changes from emulator-first to cloud namespace explorer.
  • No Event Hubs, Relay, or Notification Hubs support in this improvement track.
  • No import/export of full Azure namespace configuration in Stage 1 or Stage 2.
  • No silent receive/complete behavior for active messages.
  • No replacement of the existing MVP spec or rewrite of completed scope.

Stage Plan

Stage 1: Wire Copy Body

  • Add an app-layer clipboard abstraction.
  • Add CopyBodyCommand to MessageInspectionViewModel.
  • Enable the button only when the selected message body is copyable.
  • Add tests for active message, DLQ message, subscription message, empty selection, and empty body.
  • Add a UI smoke check for rendered command state.

Stage 2: Harden Namespace Filter UX

  • Add Ctrl+F input binding to focus and select the filter text box.
  • Prove filter reapplication after refresh.
  • Prove create/delete refresh invalidates stale filter snapshots.
  • Add UI smoke coverage for Ctrl+F focus and one recursive rendered match.

Stage 3: Dashboard Overview

  • Add dashboard row projection from loaded queue/subscription entities.
  • Add a Dashboard tab or top-level overview pane without disrupting the existing entity detail workflow.
  • Show columns: Name, Type, Active, DLQ, Scheduled, Total, Last Refreshed.
  • Highlight rows with DLQ count greater than zero.
  • Add manual refresh first; defer auto-refresh unless cancellation and busy-state tests are in place.

Stage 4: Grid Copy And Context Menus

  • Add dashboard row copy as deterministic TSV.
  • Add copy name/path context menu command.
  • Add message-grid row copy after message columns are stable.
  • Test keyboard and context-menu activation through command services before broad UI smoke coverage.

Stage 5: Optional Active Receive Workflow

  • Decide whether destructive active receive belongs in the product.
  • If approved, design receive/complete as an explicit command with confirmation and operation log entry.
  • Add integration proof that selected active messages disappear only after confirmation.
  • Keep DLQ replay/delete semantics unchanged.

Acceptance Criteria

  • Copy Body works for active messages, DLQ messages, and subscription messages.
  • Copy Body is disabled or blocked with a clear tooltip when no message body is selected.
  • Ctrl+F focuses the namespace filter and selects existing filter text.
  • Filtering preserves parent topic nodes for matching subscriptions.
  • Refresh, create, and delete operations keep the tree filter state coherent.
  • Dashboard shows one row for each queue and each subscription, not topic aggregate rows for subscriptions.
  • Dashboard count columns match SDK runtime counts from the local emulator.
  • Dashboard rows with DLQ count greater than zero are visually distinct and accessible.
  • Dashboard refresh updates both dashboard rows and selected entity counts.
  • Row/name copy formats are deterministic and covered by unit tests.
  • Any destructive receive/complete command is explicitly confirmed and separately tested.

Risks, Assumptions, And Deferred Choices

Assumptions

  • The user wants improvements that fit the current emulator-first application, not a full clone of ServiceBusExplorer.
  • The reference repository is useful for workflows and tests, but the local MVP spec remains the authoritative product contract.
  • Clipboard behavior should be abstracted because UI smoke tests can be sensitive to desktop session state.

Risks

  • Auto-refresh can create confusing concurrency unless cancellation and busy-state behavior is designed first.
  • Dashboard click-to-select behavior can fight the existing tree/detail workflow if state ownership is not explicit.
  • Active receive/complete can surprise users if it is presented like a read-only inspection command.

Deferred Choices

  • Whether dashboard becomes the default selected tab after connect.
  • Whether to implement auto-refresh and what interval controls are acceptable.
  • Whether active receive/complete belongs in this app.
  • Whether import/export should mean namespace configuration, message bodies, or both.
  • Whether cloud authentication should ever be added to an emulator-focused tool.

Definition Of Done

  • The selected stage is implemented as one vertical slice.
  • Unit tests cover command state, projection, and formatting behavior.
  • Integration tests cover emulator-dependent behavior when the stage depends on SDK/runtime state.
  • UI smoke tests cover only the rendered behaviors that cannot be proved below WPF.
  • Destructive operations remain explicit and separately confirmed.
  • The existing fast test command remains green without requiring Docker or UI automation.
  • Documentation and manual proof scripts are updated only for implemented behavior.

Notes

The reference repository's own test document is mostly an acceptance checklist rather than an automated suite. That makes it valuable as a coverage prompt, but not as a direct model for this repository's test architecture. This repo's layered test strategy is stronger for local development because emulator and WPF tests are explicitly gated.
